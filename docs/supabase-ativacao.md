# Conta e cópia remota — preparação

Não conectar a dados reais até validar segurança, privacidade e QA. A integração não está habilitada sem `NEXT_PUBLIC_SUPABASE_URL` e `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`; use a origem HTTPS do projeto, sem caminho, e chave publicável, nunca `service_role` nem chave secreta. Cadastre as variáveis no ambiente de build e execução, sem colocá-las no repositório, e execute novo `npm run build`; a CSP inclui somente essa origem HTTPS. A chave pública não substitui RLS. Habilite login por email e senha no Auth e crie duas contas fictícias de teste por procedimento autorizado, sem enviar emails; nenhuma conta é criada por esta aplicação. Entre em `/conta` e use as ações manuais. A sessão é verificada no servidor pelo Auth antes de cada operação.

Em projeto Supabase descartável, aplique `supabase/migrations/202611150001_snapshots.sql` com privilégios de migração. Execute o teste transacional em banco de teste com `psql "$TEST_DATABASE_URL" -v ON_ERROR_STOP=1 -f supabase/tests/isolation.sql`; a credencial de teste deve ter permissão para inserir usuários fictícios, trocar role e executar rollback. Não use banco de produção. Esse teste ainda precisa ser executado e complementado por teste das rotas HTTP com duas sessões reais.

Registro 18/11/2026: o teste transacional `isolation.sql` foi executado com sucesso no projeto descartável `prancheta-qa-disposable` (sa-east-1) via MCP Supabase: sem exceções em nenhuma asserção (leitura, update, delete e insert cruzados bloqueados; reatribuição de dono bloqueada; linha própria visível) e rollback verificado (0 snapshots, 0 fixtures residuais). Migração aplicada, RLS ativo com 4 políticas (`snapshots_select/insert/update/delete`) e 2 contas fictícias presentes no Auth. Pendente: teste das rotas HTTP com duas sessões reais antes de conectar produção.

O snapshot contém todos os campos da aplicação, inclusive texto de currículo; não contém PDF. O envio, restauração e exclusão são ações explícitas. Uma revisão evita que uma cópia antiga sobrescreva outra salva desde a última leitura. A exportação remota usa o formato de backup criptografado existente; restaure pelo dashboard com a mesma frase-senha. A frase-senha perdida não pode ser recuperada.

A tela de conta solicita recuperação de senha pelo Auth e permite definir uma nova senha ao voltar pelo link. Configure SMTP e permita o redirecionamento para `/conta` no domínio usado; a entrega do e-mail e o callback real ainda precisam de validação em teste.

Para habilitar exclusão da conta, configure apenas no servidor `SUPABASE_SERVICE_ROLE_KEY` do mesmo projeto, sem prefixo `NEXT_PUBLIC_`; jamais a exponha ao navegador. A rota valida o token junto ao Auth, pede confirmação textual e verifica novamente a senha da identidade verificada antes de usar `auth.admin.deleteUser`. Não aceita ID fornecido pelo cliente. Excluir Auth deve remover o snapshot por `ON DELETE CASCADE`; valide isso no projeto de teste. MFA verificado impede essa operação até existir reautenticação adequada. Uma falha de rede pode deixar o resultado incerto: verifique o estado no Auth antes de repetir. Dados locais e backups do provedor não são excluídos. O processo de retenção/exclusão de backups continua pendente. Tokens emitidos podem continuar válidos até expirar; revogação de refresh não invalida JWT imediatamente. Objetos de Storage pertencentes ao usuário podem impedir a exclusão; este projeto não usa Storage.

Validação real pendente: em projeto descartável, crie duas contas fictícias, aplique a migração, teste exportação/restauração com frase certa e errada; tente exclusão sem sessão, com senha errada, com MFA e para outra identidade; então exclua uma conta fictícia e verifique no Auth e no banco a cascata, a preservação da segunda conta e os limites de tokens e backups. Não usar dados reais. Retenção, recuperação de conta, privacidade e isolamento real ainda exigem homologação. Não foram validados login, sincronização, exclusão ou políticas em Supabase real por falta de projeto e credenciais de teste.
